  - 변경점
    # 핵심 기능 수정 전 → 수정 후
    - 작성일: 2026-09-17
    - 기준: 사용자가 마지막으로 전달한 요구사항 전체.
    - 사용자 합의: 응모와 응모권 차감 구분 / 중단과 취소 구분 / 응모 접수 완료와 관리자 판단 구분 / 나머지 용어 통일안 동의.
    - 기존 절 구성을 유지했다. 중복 14절 번호를 정리해 운영 및 시연은 15절, 공통 추가 검토는 16절로 변경했다.
    - 확정된 동작은 서술형으로 정리했다. 답변이 없는 정책과 서로 충돌하는 정책은 임의로 확정하지 않았다.
    - 이 문서는 주요 문장·용어·정책 편집 내역이다. 띄어쓰기·문장부호 등 단순 교정은 개별 열거하지 않는다.

    ## 2. 이벤트 관리
  
    수정 전: 모집 마감 후 하나의 이벤트 하나의 회차에 유효 응모자를 대상으로 추첨한다.  
    수정 후: 이벤트 하나당 모집 회차는 하나이며, 모집 마감 후 해당 이벤트의 유효 응모자를 대상으로 추첨한다.  
    이유: 확정된 회차 범위를 문장으로 명확화했다.  
    수정 전: 단일 상품을 참여자 모두가 추첨하는 방식 / 다중 상품에 대해 순위별 추첨하는 방식.  
    수정 후: 단일 경품 추첨 / 여러 경품의 등수별 추첨을 지원한다.  
    이유: 경품 용어를 통일하고 추첨 방식 표현을 정리했다.  
    수정 전: 중단·취소를 하나의 개념으로 작성.  
    수정 후: 중단은 재개 가능한 일시 정지, 취소는 재개하지 않는 최종 종료로 구분.  
    이유: 사용자 답변 2.B 반영.  
    수정 전: 중단·취소하면 응모권을 반환한다.  
    수정 후: 취소 시 반환은 유지하고, 일시 중단 시 반환 여부는 재확인 필요로 표시.  
    이유: 재개 가능한 중단에 반환까지 적용할지는 답변되지 않았다. 반환 의무를 임의로 없애거나 유지하지 않았다.  
    수정 전: 반환되는 응모권의 기한은 해당 월 / 일정 시간 후 반환.  
    수정 후: 후속 반환 처리는 유지하고, 귀속 월·반환 완료 시한·월 경계 처리를 재확인 항목으로 분리.  
    이유: 확정되지 않은 숫자와 월 기준을 만들지 않았다.  
    수정 전: 추첨 완료·발표 대기 / 발표 완료 / 중단·취소 / 재추첨.  
    수정 후: 추첨 결과 확정·발표 대기 / 결과 발표 완료 / 중단 / 취소 / 재추첨.  
    이유: 상태 명칭을 통일했다. 재추첨 상태는 원안대로 유지하며 별도 실행 유형으로 임의 변경하지 않았다.
    ## 3. 출석·미션·게임
  
    수정 전: 사용자 초기화 00시 UTC와 운영 절의 사용자·이벤트별 00시·시간대 재확인이 공존.  
    수정 후: 사용자당 하루 1회, 매일 00:00 UTC 초기화로 통일. 09:00 KST를 병기.  
    이유: 최신 기본 출석 확정 내용 적용.  
    수정 전: 일회성 미션의 이벤트 기간이 불명확하며 15절의 공통 기간 단위 결정을 참조.  
    수정 후: 서비스 공통·이벤트별 소속과 기준 기간을 재확인 항목으로 명시하고 존재하지 않는 참조 삭제.  
    이유: 소속 정책은 답변되지 않아 미정 유지.  
    수정 전: 게임 보상은 하루 1회 1장, 백오피스에서는 점수·횟수별 보상 수량 관리.  
    수정 후: 하루 1회 1장 유지. 백오피스는 게임 보상 획득 조건 관리로 표현 정리.  
    이유: 게임 고정 보상 규정에 맞췄다. 전체 게임 합산인지 게임별인지와 획득 조건은 재확인으로 유지.
    ## 4. 응모권 관리·응모
  
    수정 전: 응모권 공통 사용 확정과 7절의 사용 범위 확정 대기 문구가 공존.  
    수정 후: 공통 응모권이며 특정 이벤트에 종속되지 않고, 유효한 응모권을 응모권 사용 이벤트에 차감한다.  
    이유: 이미 확정한 정책에 맞춰 오래된 미정 표현 제거.  
    수정 전: 만료 직전 적립분의 처리 기준: 말일 이벤트 오픈.  
    수정 후: 월말 이벤트 운영은 운영 정책으로 유지. 만료 직전 지급·차감 처리 기준은 별도 검토 항목으로 분리.  
    이유: 이벤트 개설은 만료 시점의 거래 처리 기준을 대신하지 않는다.  
    수정 전: 추첨 대상 제외 시 사용 응모권 반환.  
    수정 후: 해당 이벤트 응모의 차감분 반환으로 정리. 부정 획득분의 반환 여부는 추가 검토 표시.  
    이유: 일반 반환 정책을 유지하며 부정 획득분의 처리 방식을 임의 확정하지 않았다.  
    수정 전: 총 참여자 수.  
    수정 후: 응모자 수. 사용자 중복을 제거한 인원으로 정의하고 응모 건수와 구분.  
    이유: 합의한 용어 정의 반영. 응모 건수 표시 기능은 필수 범위로 추가하지 않았다.
    ## 5. 검토·추첨·재추첨
  
    수정 전: 관리자가 참여 허용 또는 제외 결정.  
    수정 후: 관리자 '참여 허용' / '추첨 대상 제외'로 구분하고 응모 접수 완료와 별개임을 명시.  
    이유: 사용자 답변 3.A 반영. 합의된 관리자 결과명인 '참여 허용'은 유지.  
    수정 전: 응모권 사용 이벤트는 모집 마감 후 바로 추첨 / 추첨의 자동 실행.  
    수정 후: 응모권 사용 이벤트는 모집 마감 후 자동 추첨한다.  
    이유: 확정형 문장으로 통합. 자동 발표까지 확정하지는 않았다.  
    수정 전: 15분 안에 검토가 끝나지 않은 탐지 건이 남으면 보류.  
    수정 후: 미검토 탐지 건의 처리 방식을 재확인 필요로 표시하고, 15분 문구의 충돌을 기록.  
    이유: 즉시 자동 추첨과 양립하는 기준이 정해지지 않았다. 미검토 건 자동 포함·자동 제외를 임의로 택하지 않았다.  
    수정 전: 3등 → 2등 → 1등 추첨, 프론트엔드 확인 요청.  
    수정 후: 기존 순서 안은 보존하고 실제 선정 순서인지 화면 발표 순서인지 재확인 표시.  
    이유: 이전 답변의 1등 우선 권장안을 사용자가 확정하지 않았으므로 변경하지 않았다.  
    수정 전: 재추첨 수동 실행, 사유 기록, 이력 기록, 최초 추첨 출처 확인.  
    수정 후: 관리자가 사유를 입력해 수동 재추첨하고, 이력과 최초 추첨 연결 관계를 보존한다.  
    이유: 확정된 내용을 서술형으로 정리.  
    수정 전: 사용자에게 프론트적으로 보여주지 않는다.  
    수정 후: 재추첨 연출 생략인지 결과까지 비공개인지 재확인 필요로 표시.  
    이유: 본인 당첨 결과 표시·발표 요구사항과의 관계가 불명확하다.  
    수정 전: 하나의 결과만 확정 + 재추첨 지원.  
    수정 후: 최초 추첨과 각 재추첨 실행별로 하나의 결과만 확정하고 이전 결과를 덮어쓰지 않는다.  
    이유: 확정된 재추첨 이력 보존과 중복 실행 방지 요구를 함께 표현.
    ## 6. 결과 발표·알림
  
    수정 전: 11절은 관리자 확인 후 발표, 마지막 알림 절은 결과 확정 즉시 공개.  
    수정 후: 관리자 발표 승인 즉시 결과를 공개한다.  
    이유: 핵심 기능 11절의 명시적인 관리자 발표 정책을 기준으로 부속 비기능 문구를 일치시켰다. 즉시 자동 발표로 바꾸지 않았다.  
    수정 전: 결과 확정 후 화면 반영 2초 / 알림 생성 30초.  
    수정 후: 관리자 발표 승인 후 화면 반영 2초 / 알림 생성 30초.  
    이유: 발표 전 비공개 정책과 측정 시작점을 일치시켰다. 목표 수치는 변경하지 않았다.  
    수정 전: 결과와 알림 생성 작업을 같은 DB 트랜잭션에 저장.  
    수정 후: 발표 상태 변경과 알림 생성 작업 등록을 같은 DB 트랜잭션에 저장.  
    이유: 발표 전에 결과 알림이 나가지 않도록 관리자 발표 정책과 맞췄다.  
    수정 전: 이벤트 오픈시 오픈 전 알림.  
    수정 후: 응모 자격 충족 사용자에게 이벤트 시작 관련 알림을 제공하며, 시작 전·시작 시점 여부는 재확인.  
    이유: 새 알림 기능은 유지하되 발송 시점을 임의 지정하지 않았다.  
    수정 전: 이벤트·사용자·알림 유형으로 중복 방지.  
    수정 후: 기존 기준은 유지하고, 재추첨 재발표 알림의 중복 방지 기준은 추가 검토.  
    이유: 최초 발표 때문에 재발표 알림이 누락되는 경우를 확인할 수 있게 표시.
    ## 7. 백오피스·인증 승인·배너·시연
  
    수정 전: 인증 승인 기능은 취소선 처리했으나 승인 대기·승인 완료·반려 필터가 남음.  
    수정 후: 13절을 제외 기능으로 명시하고 해당 필터 제외. 지급 현황·사용자 검색·미션·기간 필터·페이지네이션은 12절로 이동.  
    이유: 제외 기능의 잔여 표현 제거. 어뷰징 검토는 유지.  
    수정 전: 배너 등록·수정·삭제 반복 기재.  
    수정 후: 한 번만 기재하고 순서·노출 기간 없음·연결·슬라이드·최대 5개 유지.  
    이유: 중복 문장만 정리.  
    수정 전: 배너 이미지 용량은 구현 시 결정, 비기능 요구사항에는 5MB 명시.  
    수정 후: 비기능 이미지 업로드 기준 적용.  
    이유: 같은 문서에 제시된 이미지 형식·용량 기준을 일치시켰다.  
    수정 전: 가상 사용자 + 더미 데이터 / 인증은 임의.  
    수정 후: 가상 사용자·더미 데이터 시연을 유지하고 시연 인증은 비기능 관리자 보호 기준을 참조.  
    이유: 실제 회원가입 기능을 추가하지 않고 관리자 보호 요구와 연결.  
    수정 전: 사용자당 또는 계정당 제한 혼용.  
    수정 후: 사용자당 제한으로 통일하고 가상 사용자도 고정 사용자 ID로 식별.  
    이유: 시연 중 사용자 전환이 보상·응모 제한을 초기화한다는 오해 방지.
    ## 8. 문서 구성 정리
    - 기본 절 순서와 핵심 기능 구성을 유지했다.
    - 운영 및 시연 범위: 두 번째 14절 → 15절.
    - 공통 추가 검토 사항: 15절 → 16절.

## 1. 이벤트 관리

### 이벤트 등록 및 관리

- 이벤트 이름, 설명, 이미지, 응모 기간을 관리한다.
- 여러 이벤트를 개설할 수 있으며, 이벤트별 경품 및 당첨 인원을 설정한다.
- 이벤트는 응모권 미사용 이벤트와 응모권 사용 이벤트로 구분한다.
- 응모권 미사용 이벤트의 필요 응모권 수는 0장이다.
- 응모 자격에 유플러스 멤버십 등급을 적용한다.
- 관리자와 임직원은 응모할 수 없다.

### 응모권 미사용 이벤트

- 응모권 차감 없이 이벤트에 응모한다.
- 원하는 경품을 선택하지 않고 이벤트 자체에 응모한다.
- 등수별 경품과 당첨 인원을 설정한다. 예: 1등 1명, 2등 5명, 3등 20명.
- 단일 경품에 당첨 인원을 설정한다. 예: 동일 경품의 당첨자 1명 또는 50명.

### 응모권 사용 이벤트

- 지정된 시각에 모집을 시작하고 정해진 시간 동안 응모를 접수한다.
- 이벤트 하나당 모집 회차는 하나이며, 모집 마감 후 해당 이벤트의 유효 응모자를 대상으로 추첨한다.
- 모집 시간은 이벤트별로 설정한다. 15시부터 15시 10분까지 모집하는 것은 예시이며, 10분으로 고정하지 않는다.
- 가중치 적용 이벤트는 여러 장의 응모권을 차감해 응모할 수 있다.
- 가중치 미적용 이벤트는 응모권 1장을 차감해 응모하며, 응모자에게 동일한 추첨 가중치를 적용한다.
- 다음 두 가지 경품 구성에 대한 추첨을 지원한다.
  1. 단일 경품을 대상으로 추첨한다.
  2. 여러 경품을 대상으로 등수별로 추첨한다.

### 수정 및 삭제 제한

- 시작 전에는 모든 설정을 수정할 수 있다.
- 진행 중에는 제목·설명·이미지를 포함한 이벤트 정보를 수정할 수 없다.
- 진행 중 경품·응모권 차감 수량·당첨 인원·마감 시각 등 응모 조건을 변경할 수 없다.
- 마감 후에는 이벤트 정보를 수정할 수 없다.
- 시작 전이며 응모 이력이 없는 이벤트만 삭제할 수 있다.
- 이벤트 중단·취소는 이벤트 정보 수정과 구분한다.
- 이벤트 중단은 일시 정지이며, 이후 재개할 수 있다.
- 이벤트 취소는 최종 종료이며, 이후 재개할 수 없다.
- 이벤트 취소 시 해당 이벤트의 응모에 차감한 응모권을 반환한다.
- [재확인 필요] 기존에는 중단·취소 모두 응모권을 반환하도록 작성했다. 일시 중단과 취소를 구분함에 따라 일시 중단 시에도 반환할지 확정한다.
- [추가 검토 필요] 일시 중단 후 재개 시 기존 응모 유지, 마감 시각 변경 여부, 재개 가능한 상태와 조건을 정한다.
- 응모권 반환은 중단·취소 처리 직후가 아닌 후속 처리로 수행한다.
- [재확인 필요] 반환 대상이 되는 중단의 범위와 반환 완료 시한을 정한다.
- [재확인 필요] 반환 응모권은 '해당 월'까지 유효하다. 해당 월이 원래 차감한 월·취소한 월·반환한 월 중 어느 월인지 확정한다.
- [추가 검토 필요] 중단·취소와 응모가 동시에 발생할 때의 처리 순서 및 월을 넘긴 반환의 만료 처리를 정한다.

### 상태 관리

- 진행 예정, 진행 중, 마감, 추첨 결과 확정·발표 대기, 결과 발표 완료, 중단, 취소, 재추첨 상태를 구분한다.
- 시스템은 이벤트 상태를 관리하며, 관리자는 허용된 상태 변경을 수행한다.
- 관리자는 추첨 결과 확정·발표 대기 상태를 결과 발표 완료 상태로 변경한다.
- 관리자는 진행 예정·진행 중·마감 상태의 이벤트를 중단할 수 있다.
- [추가 검토 필요] 취소 가능한 상태, 중단 후 재개할 상태, 재추첨 상태 진입·종료 조건을 정한다.
- '응모자 없음'과 '추첨 대상자 없음' 종료 상태를 구분한다.

## 5. 게임

- 여러 종류의 게임을 제공한다.

- 게임 점수는 서버가 판정한다.
- 게임은 횟수 제한 없이 플레이할 수 있다.
- 게임 보상은 하루 1회 응모권 1장으로 제한한다.
- [재확인 필요] 일일 보상 제한은 전체 게임 합산 기준인지 게임별 기준인지 확정한다.
- [재확인 필요] 보상 획득에 필요한 게임 플레이 횟수·점수 조건과 일일 기준 시간대를 정한다.
- 게임 어뷰징 탐지 방식은 추후 검토한다.

### 미정 사항

- [추가 검토 필요] 제공할 게임 종류 및 게임별 규칙. 타코야끼 만들기는 후보이며 확정 게임이 아니다.
- [추가 검토 필요] 게임 결과·플레이 횟수의 유효성 검증 방식. 담당: 윤태형.
- [추가 검토 필요] 재시도·중복 결과 제출의 처리 방식. 담당: 윤태형.

## 6. 응모권 관리

### 지급 및 조회

- 기본 출석, 일회성 미션, 게임 보상으로 응모권을 지급한다.
- 기본 출석 보상은 일일 1장이다.
- 게임 보상은 5절의 일일 제한과 보상 조건을 적용한다.
- 보유 응모권 수와 지급·차감 이력을 조회한다.
- 이력에서 수량, 사유, 발생 시각, 관련 행위를 확인한다.
- 포인트는 사용하지 않고 응모권으로 관리한다.

### 정합성 및 중복 방지

- 응모권 이력은 수정·삭제 없이 누적 기록한다.
- 정정이 필요하면 원본에 연결된 별도 이력을 추가한다.
- 반환 시 원본 차감 이력에 연결된 반환 이력을 추가하고 잔액과 함께 반영한다.
- 동일 차감 건의 반환 요청이 반복돼도 중복 반환하지 않는다.
- 이력 합계와 현재 보유 응모권 수의 일치를 보장한다.
- 동시 요청에서도 보유량을 초과해 차감할 수 없다.
- 같은 보상 건의 지급 요청이 반복돼도 한 번만 반영한다.

### 사용 범위·유효기간

- 응모권은 공통 응모권이며, 특정 이벤트에 종속되지 않는다.
- 유효한 공통 응모권을 응모권 사용 이벤트의 응모에 차감할 수 있다.
- 응모권은 월별로 만료하며, 만료 시점의 잔여 응모권을 소멸 처리한다.
- 응모권 상태에 '만료'를 포함한다.
- 만료도 이력으로 기록해 이력 합계와 잔액의 일치를 유지한다.
- [재확인 필요] 월별 만료 시점의 기준일·시각·시간대를 명시한다. 기존 문구는 '00시'이며, 운영 절에서는 출석과 같은 시간 기준을 적용한다.
- [추가 검토 필요] 만료 직전 지급·차감과 이미 접수 완료된 응모의 월 경계 처리 기준을 정한다.

### 응모권 경제·운영

- 추첨 대상에서 제외된 사용자의 해당 이벤트 응모에 차감한 응모권을 반환한다.
- [추가 검토 필요] 부정 획득 응모권에 대해서도 반환할지, 별도 처리를 적용할지 정한다.
- 관리자의 응모권 수동 지급·회수 기능은 이번 버전에서 구현하지 않는다.
- 월말에는 응모권 차감 수량 상한이 없는 이벤트를 열어 잔여 응모권의 사용 기회를 제공한다.
- 응모권의 유효기간은 월별로 구분하며, 별도의 차감 순서는 두지 않는다.
- 월을 넘긴 반환의 유효기간은 1절의 정책 확정 후 적용한다.

## 7. 이벤트 응모

- 이벤트 목록과 상세 정보를 조회한다.
- 응모 기간, 경품, 응모권 차감 여부, 멤버십 등급 조건, 추첨 방식, 가중치 규칙을 확인한다.
- 응모권 미사용 이벤트는 경품을 선택하지 않고 이벤트에 응모하며 응모권을 차감하지 않는다.
- 응모권 사용 이벤트는 모집 시간 내에 응모권을 차감해 응모한다.
- 가중치 적용 이벤트는 여러 장의 응모권을 차감해 응모할 수 있다.
- 가중치 미적용 이벤트는 응모권 1장을 차감해 응모한다.
- 응모권의 유효기간과 보유 수량을 검증한다.
- 같은 요청의 재시도와 새로운 응모를 구분해 중복 반영을 방지한다.
- 응모권 차감·차감 이력·응모 기록은 함께 성공하거나 함께 실패하도록 처리한다.
- 응모권 미사용 이벤트도 같은 요청의 재시도로 응모 기록이 중복 생성되지 않도록 한다.
- 내 응모 내역에서 이벤트, 응모에 차감한 응모권 수, 처리 시각, 결과, 거절 사유를 확인한다.

### 응모 횟수 및 취소

- 응모권 미사용 이벤트는 사용자당 최대 1회 응모할 수 있다.
- 가중치 미적용 이벤트는 사용자당 해당 이벤트에 1회만 응모하며 응모권 1장을 차감한다.
- 가중치 적용 이벤트는 추가 응모를 허용한다.
- 사용자의 응모 취소는 제공하지 않는다.
- 이벤트 중단·취소에 따른 응모권 반환은 1절의 정책을 적용한다.

### 마감 판정

- 서버에서 마감 전에 접수 완료된 응모만 인정한다.
- 정확히 마감 시각부터는 응모할 수 없다.
- 마감 전에 접수 완료된 응모는 응답이 마감 후 도착해도 유효하다.
- [추가 검토 필요] 서버의 '응모 접수 완료 시점'에 해당하는 처리 단계를 구현 설계에서 정의한다. 담당: 석종수. 응모 담당자와 연동 기준을 맞춘다.
- 응모권 사용 이벤트는 응모 접수 완료 시점을 기준으로 판단하며, 추첨 시점의 접속 유지는 요구하지 않는다.

## 8. 실시간 응모 현황

- 응모자 수를 표시한다. 응모자 수는 사용자 중복을 제거한 인원이다.
- 추가 응모를 포함한 접수 건수는 응모 건수로 구분한다. 별도 표시 여부는 구현 범위에 따라 정한다.
- 응모권 사용 이벤트에서는 총 응모에 차감한 응모권 수와 본인의 응모에 차감한 응모권 수를 표시한다.
- 원본 기록과 집계 결과의 일치를 보장한다.
- 당첨 확률은 표시하지 않는다.
- 현황을 자동 갱신하며, 응모 직후 결과를 바로 반영한다.
- 갱신 주기는 구현 담당자가 정한다.

- '참여 허용'은 관리자 검토 결과이며, 응모 접수 완료와 구분한다.
- 검토 상태, 검토자, 검토 시각, 사유를 기록한다.

- 구체적인 탐지 수치 및 다른 사용자 정보는 공개하지 않는다.
- 마감 검토는 마감 전 응모와 관련된 탐지 건을 대상으로 한다.
- 마감 후 단순 접속·재시도로 추첨 대기를 늘리지 않는다.
- 별도 이의 제기는 이번 버전에서 제외한다.
- [추가 검토 필요] 게임 점수에 같은 검토 절차를 적용할지 정한다. 랭킹 보상은 도입 시 별도로 검토한다.

## 10. 추첨·당첨자 관리·재추첨

### 추첨 대상 확정 및 실행

- 마감 전 접수 완료된 유효 응모를 누락·중복 없이 반영한다.
- 관리자 검토 완료 후 추첨 대상 제외 결과를 반영하고, 유효 응모 처리를 확인해 명단을 확정한다.
- 미검토 건이 없으면 유효 응모 처리 확인 후 명단을 확정한다.
- 응모권 미사용 이벤트는 명단 확정 후 관리자가 수동 추첨을 실행한다. 마감·검토 완료만으로 자동 추첨하지 않는다.
- 응모권 사용 이벤트는 모집 마감 후 자동 추첨한다.
- [재확인 필요] 자동 추첨 시점에 미검토 탐지 건이 남아 있을 때의 처리 방식을 확정한다. 기존 '15분 안에 검토가 끝나지 않으면 추첨 보류' 문구는 마감 후 즉시 자동 추첨과 충돌하므로 확정 정책으로 적용하지 않는다.
- [재확인 필요] 기존 안은 3등 → 2등 → 1등 순서로 실제 추첨하며, 앞서 당첨된 사용자를 다음 등수 추첨에서 제외한다. 실제 선정 순서인지 화면 발표 순서인지 프론트엔드와 확인한다.

### 근거 보존 및 재현

- 응모자 명단, 응모권 수, 가중치, 조건을 별도 스냅샷으로 보관한다.
- 알고리즘에 필요한 시드 또는 추첨 키, 입력 순서, 버전 등 재현 자료를 보존한다.
- 관리자는 동일 입력·조건으로 결과와 당첨 순서를 재현하고 원본과의 일치를 확인한다.
- 재현·검증 과정에서 원본 결과를 보존한다.
- 사용자에게 추첨 방식과 발표된 결과를 안내한다.
- 구체적인 알고리즘은 구현 단계에서 결정한다.
- [추가 검토 필요] 관리자가 시드를 고르거나 반복 실행해 결과를 선택하지 못하도록 시드 생성 주체와 추첨 전 고정·공개 방식을 정한다. 담당: 석종수.
- [추가 검토 필요] 스냅샷 보존 기간과 사용자 탈퇴·개인정보 파기 시 처리 방식을 정한다.

### 재추첨

- 재추첨은 관리자가 수동으로 실행한다.
- 관리자는 재추첨 사유를 입력한다.
- 재추첨은 이력에 남기며, 최초 추첨과의 연결 관계를 보존한다.
- 사용자 요청에 의한 당첨 취소와 임의 재추첨은 제공하지 않는다.
- 발표 후 자격 미달·어뷰징이 확인되면 해당 당첨자의 당첨을 취소하고 재추첨한다. 취소 대상이 아닌 기존 당첨자는 유지한다.
- [재확인 필요] '사용자에게 프론트로 보여주지 않는다'는 재추첨 연출 생략인지, 변경된 결과도 비공개로 하는 것인지 확정한다.
- [추가 검토 필요] 재추첨 후보 범위, 가중치 기준, 후보 부족 처리, 허용 기한, 재발표 방식과 기존 결과 보존 방법을 정한다.

### 가중치 및 중복 당첨

- 응모권 사용 이벤트는 가중치 적용·미적용 방식으로 구분한다.
- 가중치 적용 이벤트는 여러 장의 응모권을 차감해 응모할 수 있다.
- 가중치 미적용 이벤트는 응모권 1장을 차감해 응모하며 응모자별 추첨 가중치는 동일하다.
- 응모권 미사용 이벤트는 이벤트 단위 응모를 기준으로 추첨하며 응모자별 추첨 기회는 1회다.
- 이벤트 하나에서 동일 사용자의 중복 당첨을 허용하지 않는다. 같은 경품과 다른 경품 모두 동일하게 적용한다.
- [재확인 필요] 응모에 차감한 응모권 수를 가중치로 환산하는 계산식, 상한, 추가 배율을 정한다. 담당: 석종수.
- [추가 검토 필요] 등수별 경품 배정 순서와 당첨자를 후속 추첨에서 제외하는 처리 순서를 확정한다.

### 대상 부족 및 결과 관리

- 유효 추첨 대상자가 당첨 인원보다 적으면 전원 당첨시키고 남은 당첨 자리는 미선정으로 처리한다.
- [추가 검토 필요] 여러 경품·등수에서 대상이 부족할 때 경품 배정 우선순위를 정한다.
- 응모자가 없으면 추첨 없이 '응모자 없음'으로 종료·표시한다.
- 전원 제외되면 추첨 없이 '추첨 대상자 없음'으로 종료·표시하고 본인에게 제외 사유를 안내한다.
- 당첨자 목록, 경품 내역, 당첨 순서, 관리자 실행 이력을 관리한다.
- 최초 추첨과 각 재추첨 실행은 동시 요청·처리 중단 후 재시도에도 각각 하나의 결과만 확정한다.
- 재추첨으로 최초 추첨 결과를 덮어쓰지 않고 이력과 출처를 보존한다.

## 11. 결과 발표 및 알림

- 추첨 결과는 이벤트 유형과 관계없이 관리자 확인 후 발표한다.
- 추첨 직후 자동 발표하지 않고 발표 대기로 보관한다.
- 발표 전 당첨 결과는 비공개로 유지한다.
- 관리자가 발표를 승인하면 결과를 공개한다.
- 마감부터 발표 전까지 '응모 마감 · 결과 발표 대기'를 표시하고 내부 검토 사유는 공개하지 않는다.
- 대상 없는 종료 표시와 제외 당사자 안내는 별도로 제공한다.
- 발표 결과에는 마스킹한 닉네임과 당첨 경품을 표시한다.
- 공개 화면과 응답 데이터 모두에 마스킹을 적용한다.
- 본인 화면에는 자신의 당첨 여부와 경품을 명확히 표시한다.
- [추가 검토 필요] 구체적인 마스킹 규칙을 정한다.
- 발표 시 응모자 전원에게 결과 확인 알림을 생성한다.
- 대상, 내용, 발생 사유, 생성·모의 발송 시각, 처리 결과를 기록한다.
- 실제 이메일·푸시 대신 모의 발송한다.
- 응모 자격을 충족하는 사용자에게 이벤트 시작 관련 알림을 제공한다.
- [재확인 필요] 시작 알림은 시작 전인지 시작 시점인지, 사전 알림이면 몇 분 전인지 정한다.
- [추가 검토 필요] 시작 알림 대상 판정 시점과 이벤트 일정 변경·취소 시 예약 알림 처리를 정한다.

### 부정 획득 응모권 회수

- 관리자는 부정 획득이 확인된 응모권을 회수할 수 있다.
- 응모권 잔액을 직접 덮어쓰지 않고, 원본 지급 이력에 연결된 회수 이력을 추가한다.
- 회수 시 대상 사용자, 원본 지급 건, 회수 수량, 사유, 처리자, 처리 시각을 기록한  
다.
- 같은 지급 건에서 이미 회수한 수량을 다시 회수하지 않는다.
- 이미 만료되거나 회수된 수량은 중복 차감하지 않으며, 잔액을 음수로 만들지 않는  
다.
- 부정 획득분이 이미 응모에 차감됐다면 해당 응모를 검토한다. 제외 처리로 반환되는  
부정 획득분은 즉시 회수해 재사용을 막는다.
- 당첨 후 부정이 확인되면 당첨 취소·재추첨 정책을 적용한다.
- 사용자에게 회수 수량과 사유를 알린다.
- 임의 지급·잔액 수정은 제공하지 않고, 부정 획득분 회수만 허용한다.

## 알림

### 수신 방식

- 사용자별 사이트 내 알림함을 제공한다.
- 알림에는 제목, 내용, 생성 시각, 읽음 여부, 관련 이벤트 링크를 포함한다.
- 알림 목록 조회, 개별 읽음, 전체 읽음 처리를 제공한다.
- 실제 문자·이메일·외부 푸시는 이번 버전에서 제외한다.

## 알림

### 1. 수신 방식

- 사이트 내 알림함으로 제공한다.
- 제목, 내용, 생성 시각, 읽음 여부, 관련 이벤트 링크를 포함한다.
- 알림 목록 조회, 개별 읽음, 전체 읽음 처리를 제공한다.
- 실제 문자·이메일·외부 푸시는 제외한다.

### 2. 이벤트 시작 알림

- 대상: 해당 이벤트 알림 신청자 중 응모 자격을 충족하는 사용자
- 시점: 이벤트 시작 시 1회
- 내용: 시작 안내
- 시작 전 사전 예고 알림은 제공한다.
- 재개 시 시작 알림을 다시 생성하지 않는다.

### 3. 결과 발표 알림

- 대상: 해당 이벤트 응모자 전원
- 시점: 관리자 결과 발표 시
- 내용: 결과 확인 안내 및
- 시작 알림 신청 여부와 관계없이 제공한다.
- 관리자 발표 전에는 당첨 결과를 공개하지 않는다.

### 9. 공통 처리 기준

- 응모 관련 알림은 시작 알림 신청 여부와 관계없이 제공한다.
- 알림은 비동기로 생성한다.
- 결과 발표는 전체 알림 생성 완료를 기다리지 않는다.
- 동일 발생 건을 재처리해도 알림이 중복 생성되지 않도록 한다.
- 별도의 재개·재추첨 발표는 새로운 발생 건으로 처리한다.
- 생성 실패 시 재시도한다.
- 최종 실패 건은 관리자가 확인하고 재처리할 수 있다.
- 실제 발송은 모킹 처리한다.

## 13. 관리자 인증 승인 — 제외

- 미션 인증 제출 및 관리자 수동 승인·반려 기능은 이번 버전에서 제외한다.
- 제출 목록, 일괄 승인·반려, 승인 대기·승인 완료·반려 필터는 구현하지 않는다.
- 기존 응모권 지급 현황·검색 기능은 12절 백오피스에서 제공한다.
- 어뷰징 관리자 검토는 별개 기능이며 9절에 따라 유지한다.

## 14. 배너

- 노출 순서는 관리자가 설정한다.
- 별도 노출 기간은 두지 않는다.
- 관리자는 배너를 등록·수정·삭제한다.
- 배너는 이미지 형식이며 선택하면 연결된 이벤트 페이지로 이동한다.
- 배너는 자동 슬라이드와 좌우 화살표 이동을 지원한다.
- 배너는 최대 5개까지 등록한다.
- 이미지 형식·용량 제한은 비기능 요구사항의 이미지 업로드 기준을 적용한다.

## 15. 운영 및 시연 범위

- 로그인 화면에서 사용자 또는 관리자 역할을 선택해 진입하는 시연 흐름을 제공한다.
- 가상 사용자 선택·전환으로 사용자별 데이터를 시연한다.
- 가상 사용자와 더미 데이터로 시연하며, 동일 가상 사용자는 고정된 사용자 ID로 식별한다.
- 시연 인증 및 관리자 보호는 비기능 요구사항의 시연 로그인·관리자 보호 기준을 적용한다.
- 시간 저장·비교는 UTC를 기준으로 하고 화면에서는 KST로 표시한다.
- 기본 출석은 별도 동작으로 인정하며 사용자당 하루 1회, 00:00 UTC에 초기화한다.
- 응모권 월별 만료의 시간 기준은 출석과 동일하게 적용하며, 구체적인 기준일은 6절에서 확정한다.
- 주간 미션은 보류한다. 주간 미션·주간 랭킹의 기준 시각은 해당 기능 도입 시 정한다.
- 응모권 지급부터 응모·검토·자동 또는 수동 추첨·결과 발표·검증까지 더미 데이터로 시연한다.
- 잔액 부족, 중복 요청, 검토 대기, 제외, 낙첨, 대상 없음 등 예외 상황을 포함한다.
- 더미 데이터에서도 이력·잔액·응모·추첨 결과의 정합성을 유지한다.
- 로딩, 빈 목록, 오류, 처리 성공 등 화면 상태를 안내한다.
- 실제 외부 알림 발송, 배송·결제는 이번 범위에서 제외한다.

# 비기능 요구사항

## 1. 사용자 규모 및 요청량

- 이벤트당 응모자: 1,000명.
- 동시 접속자: 100명.
- 평시 요청량: 초당 20건(20 RPS).
- 마감 직전 요청량: 초당 100건(100 RPS)을 1분간 유지.
- 동시 접속자와 초당 요청량은 별도로 측정한다.
- 테스트 전에 조회·응모 요청 비율과 데이터량을 고정한다.

## 2. 응답 시간 및 실시간 발표

- 조회 API: p95 500ms 이하.
- 응모 API: p95 1초 이하.
- 실시간 발표: 관리자 발표 승인 후 접속 사용자 화면 반영까지 p95 2초 이내.
- 재접속한 사용자는 결과 조회 API로 발표된 결과를 확인한다.
- 발표 전 결과는 재접속·직접 조회로도 공개하지 않는다.
- p95는 전체 측정값의 95%가 해당 시간 이내라는 의미다.

## 3. 동시성 및 데이터 정합성

- 출석·미션 보상은 중복 지급되지 않아야 한다.
- 동시 응모에도 응모권 잔액이 음수가 되지 않아야 한다.
- 출석 기록과 보상 지급은 함께 성공하거나 함께 취소되어야 한다.
- 응모 기록과 응모권 차감은 함께 성공하거나 함께 취소되어야 한다.
- 최초 추첨과 각 재추첨 실행은 요청이 중복되어도 각각 하나의 결과만 확정되어야 한다.
- 마감 시 처리 중인 응모의 기준을 정하고, 추첨 대상 확정 후에는 해당 스냅샷을 변경하지 않는다.
- 초기에는 DB 트랜잭션·유일 제약·조건부 차감을 적용하고 부하 테스트 결과에 따라 보강한다.

## 4. 부하 테스트 합격 기준

- 테스트 도구: k6.
- 평시 테스트: 20 RPS로 10분간 유지.
- 마감 집중 테스트: 100 RPS로 1분간 유지.
- 응답 시간: 조회·응모 API별 목표 충족.
- 예상하지 않은 오류: 전체 요청의 1% 미만.
- 정합성 오류: 중복 지급·초과 차감·중복 결과 확정 0건.
- 마감·잔액 부족 등 정책에 따른 정상 거절은 시스템 오류와 구분한다.
- 같은 사용자의 동시 응모와 중복 요청을 별도로 검증한다.
- 서버·DB 사양, 데이터량, 요청 비율을 테스트 결과에 기록한다.

## 5. 시연 로그인 및 관리자 보호

- 역할 선택 로그인은 데모 환경에서만 활성화한다.
- 관리자 권한은 역할 선택만으로 부여하지 않고 별도 인증을 거친다.
- 사용자 역할은 서버에서 결정하며 클라이언트가 전달한 역할 값을 그대로 신뢰하지 않는다.
- 모든 관리자 API는 서버에서 인증·권한을 검사한다.
- 인증되지 않은 요청은 401, 권한이 없는 요청은 403으로 응답한다.

## 6. 이미지 저장소 및 배포 환경

- 이미지 저장소: S3 등 객체 저장소를 사용한다.
- DB 저장 정보: 이미지 파일 대신 저장소 키를 저장한다.
- 업로드 권한: 관리자만 허용한다.
- 업로드 제한: JPEG·PNG·WebP, 파일당 최대 5MB.
- 초기 배포 구성: 애플리케이션 1대 + DB.
- 실행 환경: Docker 기반.
- 통신: HTTPS를 적용한다.
- 비밀정보는 환경변수 또는 시크릿 관리 기능으로 관리하며 저장소에 커밋하지 않는다.

## 7. 로그·모니터링·백업

- 요청 로그: 요청 ID, API 경로, 응답 상태, 처리 시간.
- 오류 로그: 예외 내용, 요청 ID.
- 운영 감사 로그: 추첨 실행·추첨 대상 제외·당첨 취소·정책 변경의 처리자, 시각, 사유.
- 모니터링: CPU·메모리 사용량, 오류율, 응답 시간, DB 연결 수.
- 민감정보 보호: 비밀번호·인증 토큰 기록 금지, 개인정보 마스킹.
- DB 백업: 일 1회 수행, 7일 보관.
- 복구 검증: 시연 전 백업 데이터 복구를 확인한다.

## 8. 결과 발표 및 응모자 알림

- 결과 발표와 개인별 알림 생성을 분리한다.
- 관리자가 발표를 승인하면 즉시 결과를 공개하고, 응모자 전원 알림은 비동기로 생성한다.
- 발표 상태 변경과 알림 생성 작업 등록을 같은 DB 트랜잭션에 저장해 작업 누락을 방지한다.
- 별도 작업자가 응모자를 나누어 처리하고 실패한 작업은 재시도한다.
- 이벤트·사용자·알림 유형을 기준으로 중복 생성을 방지한다.
- [추가 검토 필요] 재추첨 결과 재발표 시 알림 대상과 중복 방지 기준을 정한다. 최초 발표 알림 때문에 재발표 알림이 차단되지 않도록 한다.
- 알림 생성 목표: 응모자 1,000명 기준 관리자 발표 승인 후 30초 이내.
- 재시도 후에도 실패한 작업은 기록하고 운영자가 재처리할 수 있어야 한다.
- 실제 문자·메일 발송은 제외하고 모의 발송과 처리 결과 기록까지 구현한다.
- 실시간 발표는 응모자 전원의 알림 생성·발송 완료를 기다리지 않는다.
